# atk AI 场景起草工作流（上下文包 → YAML）

原则：atk 负责确定性的上下文收集与校验；你（AI）负责把变更翻译成可执行的场景；
生成的场景一律是**草稿**——expect 断言必须人工评审后才算入库。

触发语："为这次改动补测试场景 / 根据提交生成用例 / 沉淀场景 / 把变更转成回归用例"，
或 smoke 提示缺场景时由 atk-smoke 流程自动调用。

## 流程

1. **拿变更上下文包**：在被测仓库根目录执行
   `atk context --base <基线> --head HEAD [--context-out /tmp/ctx.md]`
   输出即"变更上下文包"：提交记录（含说明正文）、分文件补丁、模块归属、
   受影响模块的现有场景清单（禁止重复 + 风格对齐）。
   `--format json` 可给机器消费，默认 markdown 直接阅读。
   区间无变更时直接停止，无需生成场景。

2. **编写场景**：只写上下文包补丁中有据的接口/字段/分支：
   - 正常链路与有据异常分支（如 409 冲突、422 校验）各至少一条；
   - `module` 必须取自上下文包的模块归属；`scenario` 名不得与包内现有场景清单重复；
   - 请求路径、字段名、示例值必须来自补丁或提交说明，禁止臆造接口；
   - `expect` 必须具体（响应码 + 关键业务字段），多步骤用 `capture` 传递状态；
   - `env` 沿用该模块现有场景的 env；`tags` 必须含 `ai-generated`；
   - 新建文件 `scenarios/<module>/gen-<短哈希>-N.yaml`
    （短哈希取 `git rev-parse --short HEAD`，N 从 1 递增；只增不改）。

3. **校验与实测**：`atk validate` 通过后，向用户展示草稿路径与 expect 清单请人评审；
   评审通过再 `atk run --tags ai-generated` 实测。把实测结论与需人定性的 expect 一并交人确认。

## 禁止事项

- 不得修改既有场景文件（起草只增不改）。
- 不得跳过 validate 直接宣称"场景已入库"；validate 未过不得跑 run。
- 不得为补丁中不存在的接口/字段编造步骤；无依据的分支宁可不写。
