atk 人机协作使用说明

atk 是一个 AI 原生的双层自动化测试框架：AI 干量产的活（起草场景、实测、回填证据），人做判断的事（审断言、定性失败），机器守确定的门（gate）。本文面向使用者：怎么安装、怎么接入项目、日常怎么和 AI 配合。命令的完整参数手册见 docs/USAGE.md，设计取舍见 docs/superpowers/specs/。

先装起来（30 秒）： 
# 1) 装 uv（已装可跳过；Windows 用 PowerShell 跑 astral 的 install.ps1）
curl -LsSf https://astral.sh/uv/install.sh | sh      # 或：brew install uv

# 2) 把 atk 装成全局命令（editable：框架代码改了即生效，不用重装）
uv tool install --editable "/path/to/auto_test_framework[console]"

# 3) 验证
atk --help
[console] 是 Web 控制台 extras（fastapi/uvicorn/apscheduler），必须写在路径引号内——写在引号外会被 uv 当成第二个位置参数而报错。

1. 安装 / 升级 / 卸载

场景命令说明
自己机器上用（推荐）uv tool install --editable "/path/to/auto_test_framework[console]"editable 安装：改框架源码立即生效，不需要每次重装。
只要命令行、不要控制台uv tool install --editable "/path/to/auto_test_framework"不带 extra；API 冒烟全功能都在基础依赖里。
给 CI 用（固定版本）uv tool install /path/to/auto_test_framework非 editable，装的是当前磁盘状态；发布后用 uv tool install dev2atf[console]。
参与框架开发uv tool install --editable "/path/to/auto_test_framework[dev]"带上 pytest；跑测试：cd auto_test_framework && python -m pytest。
升级uv tool upgrade dev2atf（发布版）
uv tool install --force --editable "/path/to/auto_test_framework[console]"（本地版重装）		本地 editable 版改代码即生效，一般不需要重装。
卸载uv tool uninstall dev2atk注意工具名跟包名走（dev2atf）。

装好后 atk 命令在任意目录可用。atk init 走 Path.cwd()——和 git init一个套路：在哪个目录跑，就是给哪个项目接入。

2. atk 是什么：两层 + 三方分工

即时层（冒烟）
每次提交 / 每个 MR 前跑。输入是变更 diff + 影响面分析，产出临时场景 → 当前环境实测 → 当次结论。不落库。
沉淀层（回归）
夜间 / 周级 / 手动跑。执行固化的 YAML 场景库，产出运行记录 + 报告，入库维护。
谁负责什么不负责什么
人业务判断：审 AI 写的断言、定性 suspect/失败、整单确认、终端里铸审批凭证不背流程、不逐条点页面、不手工抄结果
AI（Agent）按 atk agent 的 next 推进全流程；起草场景；用浏览器实测 UI 并回填证据不自己说"通过"、不代答人工介入点、不绕过 gate
atk（机器）确定性执行、结构化记录、HTML/JUnit 报告、合并门禁判定不猜业务正确性、不放行没有证据的结论

3. 接入一个被测项目（三步）

人只需要回答两个问题：被测服务在哪、先建哪些模块。

cd /path/to/被测项目

# ① 一步生成：环境 + 模块映射 + 首批健康检查场景 + AI 工作流 skill（只建缺失，绝不覆盖）
atk init --url http://127.0.0.1:8080 --modules order,coupon \
  --var 'token=${env:ATK_TOKEN}'    # 凭据形态自定，可多次；敏感值用 ${env:VAR} 占位符不入库

# ② 先看清会跑什么，再真跑
atk validate
atk run --dry-run                    # 只列选中场景，不执行
atk run --env local                  # 健康场景应已通过——流程转起来了

# ③ 之后交给 AI / CI
atk smoke --base main --title "优惠券下单" --format json
init 参数作用
--url <base_url>被测服务地址（环境名用 --env-name 指定，默认 local）。
--modules order,coupon首批模块：每个模块自动生成一张「健康检查」场景（只要求服务有响应），目录名即模块名。
--var token='${env:ATK_TOKEN}'注入凭据。vars 默认为空、没有任何必填项；${env:VAR} 在加载期从环境变量解析，缺失按受阻拦下（见 §7）。
--ui-tool ego-browser指定 AI 实测 UI 用的浏览器工具名（默认 ego-browser），写进生成的 skill 正文。
什么都不传生成 demo 示例配置，供照着改。

4. 日常循环：AI 主导，人只在中途被叫停

不要背流程。不知道下一步做什么，就问它：

atk agent --format json

返回的 next 是可直接执行的命令列表，按序跑完再问一次（状态会变，命令会变）。state 是当前环节，blockers 非空先解阻塞。requires_human: true 时必须停下，把 human_prompt 原样转给开发者——AI 不得代答。

人：给一句话（"帮我测下这次改动" / 一个基线引用） │ ▼ AI：atk smoke --base <基线> --title "<功能>" --format json ← plan→run→report→gate 一次做完 │ ▼ AI：atk agent --format json ──► 按 next 逐条执行，跑完再问 │ ├─ ui: 步骤待实测 ────────► AI 用 ego-browser 打开同一 env 的 base_url 实测， │ 截图落盘，atk record --from-json 批量回填 │ ├─ 草稿/断言要人审 ──────► 【介入点 1】停下：人终端 atk approvals mint <文件> │ 铸凭证 → atk review-draft --approval <码> 转正 │ └─ 门禁放行但未整单确认 ──► 【介入点 2】停下：人 atk review --by <姓名> --verdict approve │ ▼ AI：把 gate 的 blocking / warnings 原文摘要给人，重点讲 fail 与 suspect。 合不合并由人和 CI 判，AI 不替人下"可以合并"的结论。

4.1 常用命令速查

命令什么时候用
atk smoke --base <基线> --title "..." --format json一键冒烟（AI 主入口）。--dry-run 只列会跑什么；--module m 只跑一个模块。
atk run [--env e] [--module m] [--tags t] [--set k=v] [--skip-ui] [--dry-run]手动跑沉淀层场景库。--record-to <id> 并回计划建的记录；--record-new 新起一条（无基线，不可作门禁依据）。
atk record --last --from-json result.jsonUI 实测批量回填（推荐）。单条：--title "..." --status pass|fail|suspect|blocked --note "..." --evidence 截图。
atk gate <run_id> [--format json]合并门禁判定。--allow-unbound 是明知故犯的逃生门（warnings 留痕）。
atk context --base <基线> --format json给 AI 的确定性变更上下文包（起草场景前先拿它）。
atk report <run_id> / atk last渲染 HTML 报告 / 看最近一条记录。
atk approvals mint <文件> / list终端铸一次性审批凭证 / 看账本。--grandfather --by <人> 存量场景一次性批量转正。
atk validate / atk purge场景库自查 / 按 manifest 指纹删 init 生成物（手写内容一律保留）。

4.2 退出码（CI 用 test $? -le 1 区分"业务不通过"与"没测成"）

码含义典型原因
0通过 / 放行全部断言成立
1用例失败断言不成立（含隐式 status<400）、配置错误（call 格式、变量未解析、操作符拼错）
2没测成环境受阻（服务不可达、凭据缺失）、选中 0 个场景（含 --skip-ui 后只剩 UI 场景）、场景库有文件加载不了、记录不存在

5. UI / E2E 怎么测

atk run 自己不执行 ui: 步骤——遇到就登记为「待实测」意图并停下。UI 实测由 AI 用浏览器工具完成：

# 1) 清单来源：smoke 返回的 intents_pending（意图标题 = 场景的 scenario 名）
# 2) AI 用 ego-browser 打开"同一个 env"的 base_url，按意图标题操作；意图是业务语言，不是坐标脚本
# 3) 关键状态截图必须真落到磁盘（如 /tmp/atk-order.png）
# 4) 批量回填：title 必须一字不差对上，run_id 由 payload 自带
atk record --last --from-json /tmp/atk-ui-result.json

状态语义：pass 成立 / fail 复现（note 必含重现步骤）/ suspect 疑似需人定性 / blocked 环境或权限原因没测成。环境/账号问题记 blocked，不得记 fail；是什么就记什么。本轮确实不测 UI 才用 atk run --skip-ui——它连待实测意图都不登记，等于对外声明这次没测 UI。

6. Web 控制台（可选）

atk console                 # 前台起，默认随机端口；--port 8900 指定
atk console -d              # 后台常驻；状态与日志在 <root>/.atk/console-<端口>.{json,log}
atk console --status        # 看跑没跑
atk console --logs          # 看输出
atk console --stop          # 停（走进程组，连带全局模式拉起的子控制台）
atk console -g              # 全局模式：多项目聚合仪表盘

控制台是 YAML 的视图和编辑器，不是第二套存储：场景表单/源码双模式编辑（保存带 mtime 校验，外部改过会 409）、执行与 SSE 实时日志、运行历史与截图证据、environments/modules/schedules 设置、定时任务（control 停了就不触发，不补跑）。控制台的运行按钮走的是 atk run --record-new，产出的记录未绑基线——界面会明示"不可作合并门禁依据"。

7. 硬规则速查

规则为什么 / 违反会怎样
凭据不入库：${env:VAR} 加载期解析，缺失即按受阻拦下（exit 2）空 token 打到线上只会拿到 401，那会被误读成产品回归；atk 选择"没测成"。
空跑不算通过：选中 0 个场景 = exit 2模块名打错、场景库为空都不可能"静默全绿"。
记录必须绑基线：run --record-new 的记录过不了 gate没描述"哪次变更被测过"就不能当合并依据。合并前用 atk plan/smoke --base 建记录。
断言必须人审过：门禁只认审批账本里以断言面指纹为键、带有效签名的记录删 tag、手写账本条目都不算数；改一条断言指纹就变，必须重审。存量场景一次性批：atk approvals mint --grandfather --by <人>。
不手改 reports/runs/<id>/run.yaml当前态与 events.yaml 的 HMAC 链交叉校验，改了会被判"结论不可信"。要改结论就重跑。
AI 草稿的 expect 交人审定；AI 不得自批mint 强制交互式终端（stdin/stdout 都是 TTY），AI 驱动的 shell 一律 exit 2——这是设计，不是故障。
已有等价场景时复用不重写判重看 calls + expects 语义，不看场景名。

8. 目录布局

布局判定位置
新（.atk/）atk init 生成一切产物在 .atk/：scenarios/、environments.yaml、modules.yaml、reports/runs/、fixtures/、skills/、last-run.json、manifest.json
旧（legacy）根目录存在 scenarios/ 或 config/ 或 reports/ 任一散在根目录；命令原样工作，显式传 --root/--env-file/--runs-dir 永远优先

.atk/ 下场景库与配置照常提交 git（YAML 是唯一事实源）；init 生成的 .gitignore 只忽略可再生产物（reports、last-run、manifest、deps 账本、console 运行时文件），并显式声明 .atk/approvals.yaml 必须提交——CI 的 gate 要验签，而 mint 只能在交互式终端执行。

9. 排障

现象原因与处理
exit 2 + "环境变量未设置"${env:VAR} referenced 的环境变量没配。请求没有发出——配好后重跑。这是"没测成"，不是用例失败。
exit 2 + "选中 0 个场景"过滤条件没命中；或 --skip-ui 跳过了全部纯 UI 场景。先 --dry-run 看选中了什么。
gate 拦截 "未绑定任何 Git 基线"记录是 run --record-new 造的。用 atk plan/smoke --base <基线> 重建记录再跑。
gate 拦截 "N 份场景的断言未经人工审批"记录里的场景没批过。新场景走 mint + review-draft；存量场景 atk approvals mint --grandfather --by <人>。
gate 拦截 "变更已漂移 / head 已前进"记录建好后又改了代码或提交。重新 plan。
"变量未解析 ${x}"capture 没产出该变量（现在当步就会失败并点名路径）、环境 vars 拼写、或场景间变量隔离。优先级：env < fixture < --set < capture。
"非 git 仓库" / diff 失败在仓库根目录跑，或显式 --repo/--base；拿不到基线时 plan 自动跑全库（fail-safe，绝不空选）。
坏 YAMLexit 2（不是 1）——库问题不是产品回归。atk validate 会指出文件和重名。
