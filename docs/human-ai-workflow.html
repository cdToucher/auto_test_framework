atk 人机协作使用说明

本文说明当前项目应该如何被人和 AI 一起使用。核心原则是：人只做业务判断，AI 负责流程推进，atk 负责确定性记录和门禁。本版重点：把人工配置门槛压到「一条命令」，并给出复杂 demo 项目供全流程验证。

当前边界：atk 已支持 API 场景确定性执行、变更上下文、运行记录、报告和强化版 gate（head commit 内容一致性、未评审草稿、UI 未回填、空结果记录都会拦截）。ui: 步骤可以写入 YAML，但 atk run 内部尚未真正执行 UI，只标记为「待实测」；UI/E2E 由 AI 使用浏览器工具实测后，通过 atk record --last --from-json 回填证据（--status 必须显式给出，无默认值）。atk console 仅供本机回环访问，不需要登录口令；被测服务凭据由环境变量注入，缺失会显式告警而不是静默变空串。 本地全流程示例：简单版 SPA Shop Dogfood，复杂版见下文 §4（shop_pro）。

0. 三条命令起步（人工配置的最低门槛）

接入一个新项目，人只需要回答两个问题：被测服务在哪、想先建哪些模块。其余交给 atk 和 AI。

cd /path/to/被测项目

# ① 一步生成配置 + 首批可跑场景 + Agent skill（只建缺失，绝不覆盖）
atk init --url http://127.0.0.1:8080 --modules order,coupon

# ② 确认场景库合法、选择条件符合预期（dry-run 不执行）
atk validate
atk run --env local --dry-run        # 看清"会跑哪些、用什么环境"
atk run --env local                  # 健康检查场景应已通过 —— 流程已经转起来了

# ③ 之后由 AI/CI 接手
atk smoke --base main --title "优惠券下单" --format json
init 参数代替了原来的哪步手工配置
--url <base_url>手改 config/environments.yaml 的 base_url（环境名可用 --env-name 指定，默认 local）。
--modules order,coupon手写 modules.yaml 条目 + 手建 scenarios/<模块>/ 与第一个场景：现在每个模块自动生成一张「健康检查」场景（断言 status: "< 500"，起步只要求服务有响应），目录名即模块名，不会踩 module/目录不一致。
--var token='${env:ATK_TOKEN}'手改 vars 段。vars 默认为空、username/password 不是必填——token、cookie、api_key 型项目按键值注入自己要的即可（可多次），敏感值写 ${env:VAR} 占位符不入库。
什么都不传退回旧行为：生成 demo 示例配置，供照着改（vars 留空 + 注释示例，不再写死 testuser/testpass）。
产物收束与 AI 可见性：atk init 的全部落盘物收进单一 .atk/ 目录 （environments/modules/scenarios/fixtures/reports/skills/manifest），项目根只多一个 AGENTS.md——Codex、OpenCode、Claude Code 等主流 TUI/CLI 会自动加载它， 区块内给出命令速查、硬规则和 .atk/skills/*/SKILL.md 正文索引，AI 由此进入工作流； 不再创建 .claude/、.cursor/ 散落拷贝。反悔用 atk purge： 按 manifest 内容指纹只删 init 生成且未手工改动的物料，你写的场景与改过的配置一律保留。 历史项目（已有 scenarios/、config/、reports/）自动识别为旧布局，一切命令原样工作。
modules.yaml 现在是可选项。不配置代码→模块映射时，smoke 自动全量执行（慢但绝不漏测）；映射配好后才享受"按变更增量选场景"。凭据永远不入库：环境 vars 用 ${env:VAR} 注入，临时参数用 atk run --set key=value（优先级高于 env vars 与 fixture，capture 运行时提取值仍最高）。

1. 一句话分工

角色做什么不做什么
开发 提供需求/分支/基线；审 AI 草稿里的 expect；最终整单确认。 不手工重复点冒烟主流程；不审长篇推理。
QA 维护业务断言质量；定性 fail/suspect；补充关键业务边界。 不把日常精力放在机械点击和重复写测试代码。
AI Agent 读代码和 diff；按 atk-authoring 协议起草 API/E2E 场景；运行校验；浏览器实测；结构化回填；汇报 gate。 不直接决定合并；不编造接口/字段/页面；不口头宣称通过。
atk/CI 输出确定性上下文；执行 YAML 场景；保存 run 记录；生成报告；执行强化版 gate。 不内置 LLM 生成命令；不替代人的业务判断。

2. 目标工作流

需求讨论 -> SPEC / design -> AI coding -> AI review -> 人工 review（可选） -> AI test（当前项目） - atk smoke 建单并执行已有场景（plan -> run -> report -> gate） - 无覆盖时 atk context + AI 起草 API/E2E 草稿 - 人审 expect，atk review-draft 转正或驳回 - atk smoke 重新执行转正后的场景，产出当前 run 记录 - AI 浏览器实测 UI/E2E intent，atk record --last 回填证据 - 人做整单确认，atk review --last 落盘 - atk gate --last 输出结论 -> CI -> QA 体系测试 -> 验收

3. gate 现在到底拦什么（先建立信任）

门禁是这套流程能被依赖的前提，当前 atk gate 的判定全部基于结构化记录，不接受口头结论：

检查项结论为什么
变更文件清单与运行记录不一致拦截测的不是现在要合的代码，需重新 plan。
head commit SHA 与记录时点不同拦截文件清单没变但内容变了（amend/rebase）同样不能放行。
存在用例失败（断言/配置错误）拦截真实失败或场景写错。
意图存在 fail/suspect拦截suspect 必须 QA 定性，不允许沉默。
UI 意图仍是 pending（未实测回填）拦截没测过就不能说通过。
运行记录里有用例在运行时是 AI 草稿且未评审转正拦截判定点取运行时刻+磁盘并集：跑完草稿再 reject 移走也绕不过去。
记录里没有任何场景结果与意图拦截空跑不构成"通过"的证据。
工作区有未提交文件；环境/账号受阻；开发未整单确认仅告警提示风险但不代替人决策。

与之配套，atk run/atk smoke 在选中 0 个场景时按受阻处理（exit 2）——模块名打错、场景库为空都不可能"静默全绿"；确需空跑用 --allow-empty。未解析的 ${var} 会在发请求前拦截报配置错误，${env:VAR} 缺失会显式告警，拼写错误不再伪装成业务失败。

4. 复杂 demo：优惠券商城 Pro（shop_pro）

examples/shop_pro.py 是一个刻意做"脏"的演示系统，用来验证 atk 处理真实项目复杂度的能力：登录鉴权、商品库存、购物车校验、五种优惠券规则（满减/折扣/门槛/过期/每人限用）、订单状态机（pending→paid/cancelled，非法迁移 409）。配套 scenarios/shop_pro/ 按模块目录组织 13 张场景：auth/（正反登录）、shop/（货架、404、券三态）、order/（金额计算、状态机、重复用券、门槛、库存、空车、UI 闭环）。

# 终端 A：起演示服务（含简易页面，供 AI 浏览器实测 UI 场景）
python -m examples.shop_pro            # http://127.0.0.1:8788

# 终端 B：沉淀层回归一把梭
atk validate
atk run --tags shoppro                 # 11 个 API 场景应全过，UI 场景登记为待实测
# 回归重跑前重置演示状态（券每人限用一次是真实业务规则）：
curl -X POST http://127.0.0.1:8788/api/dev/reset

这条链路覆盖了：fixture 数据（fixtures/shop_pro.yaml）、变量捕获链、整数保留（qty: "${shop_qty}" 注入保持 int 类型）、状态码+业务字段双重断言、以及 ui_pending → AI 实测 → record --from-json → gate 的完整人机接力。端到端自动化版见 tests/test_shop_pro_dogfood.py（含 smoke→拦截→回填→放行全链）。

5. 开发如何使用

开发的交互应尽量短。推荐只给 AI 三类信息：要测的需求、基线分支、环境名。

开发对 AI 说

验证这次改动。
基线：main
环境：staging
需求：优惠券下单后金额应扣减，重复使用同一张券应失败。

开发的两个确认点

确认点开发看什么开发怎么操作
1. 审草稿 expect 只看场景名、请求/页面动作摘要、expect 断言和 AI 标出的疑问。 atk review-draft <draft.yaml> --by <name> --verdict approve|reject
2. 整单确认 看报告里的失败、疑似、受阻、截图证据和 gate 结论。 atk review --last --by <name> --verdict approve|reject
给人的输出要短：AI 不应让开发读完整 diff、完整日志或长篇分析。开发只判断业务断言是否正确，以及整次测试结论是否可接受。

6. AI Agent 如何使用

AI 的任务是把一次需求或提交推进成结构化测试记录。不要调用不存在的内置生成命令；用 atk 的确定性命令加自己的代码理解能力。

6.1 先建单，再补事实

# 默认入口：一次完成 plan -> run -> report -> gate，JSON 只输出最终 manifest
atk smoke --base main --head HEAD --env staging --title "优惠券下单" --format json \
  > /tmp/atk-smoke.json

# 只有发现覆盖不足或要起草场景时，再读取确定性上下文
atk context --base main --head HEAD --format json > /tmp/atk-context.json

smoke 会写入 .atk/last-run.json。AI 应读取 manifest 的 failed_scenarios、intents_pending 和 next（next 是可直接执行的命令模板，状态刻意留占位符），而不是从终端输出手工搬运 run_id。atk plan 仍可单独建运行记录，但不是功能验证的默认入口。

AI 必须读取：变更文件和 patch、受影响模块、现有场景（避免重复）、相关 controller/router/service/component/schema、需求说明或提交说明中的业务约束。

6.2 生成 API 场景

API 场景必须来自代码事实，按证据优先级生成：

证据AI 要提取什么
路由/controllermethod、path、query/path/body 参数。
DTO/schema/OpenAPI字段名、类型、必填、枚举、响应结构。
service/handler业务分支、状态机、权限、幂等、错误码。
现有场景登录方式、token、fixture、capture 风格。

API 场景要求：每个场景一个业务意图；expect 必须包含 status 和关键业务字段；不得只断 status: 200；不得编造不存在的接口、字段或错误码；草稿必须带 ai-generated tag；场景所在目录名应与 module 字段一致（目录即模块，否则 --module/影响面分析按字段匹配会落空，validate 会告警）。

断言能力（别再只断 status）：除相等外，expect 还支持比较、包含、正则、长度、类型、枚举；字面量以反斜杠开头可转义。 
expect:
  status: 200
  data.orderNo: not_null
  data.payAmount: "< 90"          # 比较：< <= > >= == !=
  data.msg: "contains: 成功"        # 包含 / not_contains
  data.mobile: "regex: ^1[3-9]\\d{9}$"
  data.items: "len: 3"             # 或 "len: 1..5"
  data.id: "type: str"
  data.state: "in: [pending, paid]"
  data.err: is_null
复杂值可用列表式：expect: [{ path: data.payAmount, op: lte, value: 90 }]。 
scenario: 优惠券下单后金额扣减
module: order
priority: P0
tags: [ai-generated, smoke, api]
env: staging
steps:
  - api:
      call: "POST /api/login"
      body: { username: "${username}", password: "${password}" }
      expect: { status: 200, data.token: not_null }
      capture: { token: "data.token" }
  - api:
      call: "POST /api/orders"
      headers: { Authorization: "Bearer ${token}" }
      body: { skuId: "${test_sku}", qty: 1, coupon: "WELCOME10" }
      expect: { status: 200, data.discount: 10 }
      capture: { order_no: "data.orderNo" }

6.3 生成 E2E/UI 场景

E2E 场景也必须来自代码或页面证据：前端路由与页面入口、表单字段/按钮/文案、data-testid 等稳定定位线索、页面调用的 API。UI 步骤写业务语义，不写坐标，不写"页面正常"。当前 atk run 不执行 UI，UI/E2E 的确定性结果来自 AI 浏览器实测后的 record。

scenario: 页面下单后列表显示待支付
module: order
priority: P0
tags: [ai-generated, smoke, e2e]
env: staging
steps:
  - ui:
      action: 打开订单创建页面，填写商品、数量和优惠券并提交订单
      expect: 提交成功后跳转到订单列表或详情页
  - ui:
      action: 在订单列表搜索刚创建的订单
      expect: 列表出现该订单，状态为待支付，金额已扣减优惠券

6.4 校验草稿

atk validate

# 人确认 expect 后才转正；reject 必须补 --note
atk review-draft scenarios/order/gen-abc123-1.yaml --by dev --verdict approve

# 转正后重新建单并执行
atk smoke --base main --head HEAD --env staging --title "优惠券下单" --format json

如果失败，AI 先判断失败类型：

失败类型处理
配置错误（含 变量未解析 ${...}、fixture 缺失、call 格式）修正 env、fixture、变量拼写、请求格式；这不是业务失败。
环境错误（连接/超时，自动重试后仍失败）记录 blocked 或提示检查环境；exit 2 不会污染用例结论。
断言失败不要擅自改成 pass；整理证据给人判断。
UI 待实测（ui_pending）用项目配置的浏览器工具实测，并通过 record --last 回填；未回填时 gate 拦截。
选中 0 个场景选择条件写错或场景库为空：先 run --dry-run 核对，空库按 §0 起步。

7. AI 浏览器实测与回填

AI 使用项目配置的浏览器工具（atk init 默认写入 ego-browser）完成 UI/E2E intent 后，必须把结论写回 atk 运行记录。

{
  "title": "页面下单后列表显示待支付",
  "status": "pass",
  "note": "创建订单后在列表查到该订单，状态待支付，金额已扣减优惠券",
  "evidence": ["/tmp/atk-order-list.png"]
}

atk record --last --from-json /tmp/atk-ui-result.json
status何时使用要求
pass断言明确成立最好带截图证据。
fail问题可复现必须带 note，写复现步骤和证据。
suspectAI 不确定，疑似问题必须带 note，等待人定性，gate 拦截。
blocked登录、权限、环境、服务不可用说明阻塞原因，不得标 pass。

status 没有默认值：无论命令行还是 JSON，都必须显式给出——回填即表态。pending 由含 ui: 步骤的运行自动登记，不能作为 record 的值；同名 title 回填会原地更新该 pending 意图（不会重复追加，也不会把旧的 pass 再算一份）。

8. 完整命令流程

AI 主导，本地/TUI 中执行

# 1. 建测试单并跑已有确定性场景（--format json 只输出 manifest，含 next 建议）
atk smoke --base main --head HEAD --env staging --title "优惠券下单" --format json

# 2. 如发现缺场景，AI 按 docs/AI_AUTHORING_PROTOCOL.md 起草 YAML
atk context --base main --head HEAD --format json > /tmp/atk-context.json

# 3. 校验草稿；人审 expect 后转正或驳回
atk validate
atk review-draft scenarios/order/gen-abc123-1.yaml --by dev --verdict approve

# 4. 转正后重新 smoke，得到覆盖草稿的新运行记录
atk smoke --base main --head HEAD --env staging --title "优惠券下单" --format json

# 5. AI 浏览器实测 UI/E2E 后回填（--last 免拼 run_id）
atk record --last --from-json /tmp/atk-ui-result.json

# 6. 人做整单确认
atk review --last --by dev --verdict approve

# 7. 输出门禁结论
atk gate --last --format json
atk report --last
run_id 不必手工搬运：plan / smoke / run --record-new 会把 run_id 写入 .atk/last-run.json，后续 record / report / review / gate 一律用 --last；atk last 可查看当前操作对象。 run --record-to 重复执行同一记录是幂等的（按场景覆盖，不累积重复条目）。
UI 步骤不再"必然受阻"：atk run 遇到 ui: 步骤会标记为 待实测（既不计失败也不计受阻），并自动登记为 pending 意图。 AI 实测后 atk record --last 回填；未回填前 atk gate 拦截。 门从 run 阶段移到 gate 阶段，既消除误报噪音，也保证"没测过不会说通过"。 如确需忽略 UI，用 atk run --skip-ui。

CI 中执行

# 推荐：CI 以 smoke 为单一入口；输出为机器可读 manifest
atk smoke --base origin/main --head HEAD --env staging --title "$PR_TITLE" \
  --junit reports/junit.xml --format json > reports/atk-smoke.json

# UI 待实测、草稿未转正、断言失败、变更/内容漂移、空选中都会让 gate/run 返回非 0。
# 需要检查当前记录时：
atk last --format json

9. 防漂移规则

  • AI 不得编造接口、字段、状态码、页面入口、业务文案。
  • AI 不得把环境/账号问题写成业务失败，也不得把 blocked 改成 pass。
  • AI 不得修改既有场景；草稿只增不改。
  • AI 不得跳过 atk validate 和草稿实测；回填必须显式给 status。
  • 人只审业务断言，不承担命令编排和日志归纳。
  • CI 只信 atk 运行记录和 gate，不信聊天记录中的口头结论；gate 同时校验文件清单与 head commit 内容一致性。
