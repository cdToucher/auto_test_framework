atk 人机协作使用说明

本文说明当前项目应该如何被人和 AI 一起使用。核心原则是：人只做业务判断，AI 负责流程推进，atk 负责确定性记录和门禁。

当前边界：atk 当前已经支持 API 场景确定性执行、变更上下文、运行记录、报告和 gate（含 UI 未回填拦截）。ui: 步骤可以写入 YAML，但 atk run 内部尚未真正执行 UI，只标记为「待实测」；UI/E2E 由 AI 使用浏览器工具实测后，通过 atk record --last --from-json 回填证据。atk console 仅供本机回环访问，不需要登录口令；被测服务凭据由环境变量注入。 实际本地 dogfood 示例见 SPA Shop Dogfood 全流程。

1. 一句话分工

角色做什么不做什么
开发 提供需求/分支/基线；审 AI 草稿里的 expect；最终整单确认。 不手工重复点冒烟主流程；不审长篇推理。
QA 维护业务断言质量；定性 fail/suspect；补充关键业务边界。 不把日常精力放在机械点击和重复写测试代码。
AI Agent 读代码和 diff；按 atk-authoring 协议起草 API/E2E 场景；运行校验；浏览器实测；结构化回填；汇报 gate。 不直接决定合并；不编造接口/字段/页面；不口头宣称通过。
atk/CI 输出确定性上下文；执行 YAML 场景；保存 run 记录；生成报告；执行 gate。 不内置 LLM 生成命令；不替代人的业务判断。

2. 目标工作流

需求讨论 -> SPEC / design -> AI coding -> AI review -> 人工 review（可选） -> AI test（当前项目） - atk smoke 建单并执行已有场景（plan -> run -> report -> gate） - 无覆盖时 atk context + AI 起草 API/E2E 草稿 - 人审 expect，atk review-draft 转正或驳回 - atk smoke 重新执行转正后的场景，产出当前 run 记录 - AI 浏览器实测 UI/E2E intent，atk record --last 回填证据 - 人做整单确认，atk review --last 落盘 - atk gate --last 输出结论 -> CI -> QA 体系测试 -> 验收

3. 新项目接入

人只需要完成一次基础配置，后续由 AI/CI 按协议使用。

cd /path/to/被测项目
atk init

# 1. 配环境
$EDITOR config/environments.yaml

# 2. 配代码路径到测试模块的映射
$EDITOR config/modules.yaml

# 3. 校验
atk validate

人需要填写的最小配置

# config/environments.yaml
staging:
  base_url: "https://staging.example.com"
  vars:
    username: testuser
    password: "${env:ATK_PASSWORD}"

# config/modules.yaml
modules:
  order:
    - "src/order/**"
    - "frontend/src/pages/order/**"

被测服务凭据与本地控制台

atk console 固定监听 127.0.0.1，供本机使用，不做登录鉴权。Cookie、token 等是被测服务的凭据，应在环境配置中以 ${env:VAR} 引用，而不是传给控制台：

# config/environments.yaml
staging:
  base_url: "https://staging.example.com"
  vars:
    service_cookie: "${env:ATK_SERVICE_COOKIE}"
    service_token: "${env:ATK_SERVICE_TOKEN}"

# 控制台和它启动的 atk run 都继承这些变量
ATK_SERVICE_COOKIE="..." ATK_SERVICE_TOKEN="..." atk console

4. 开发如何使用

开发的交互应尽量短。推荐只给 AI 三类信息：要测的需求、基线分支、环境名。

开发对 AI 说

验证这次改动。
基线：main
环境：staging
需求：优惠券下单后金额应扣减，重复使用同一张券应失败。

开发的两个确认点

确认点开发看什么开发怎么操作
1. 审草稿 expect 只看场景名、请求/页面动作摘要、expect 断言和 AI 标出的疑问。 atk review-draft <draft.yaml> --by <name> --verdict approve|reject
2. 整单确认 看报告里的失败、疑似、受阻、截图证据和 gate 结论。 atk review --last --by <name> --verdict approve|reject
给人的输出要短：AI 不应让开发读完整 diff、完整日志或长篇分析。开发只判断业务断言是否正确，以及整次测试结论是否可接受。

5. AI Agent 如何使用

AI 的任务是把一次需求或提交推进成结构化测试记录。不要调用不存在的内置生成命令；用 atk 的确定性命令加自己的代码理解能力。

5.1 先建单，再补事实

# 默认入口：一次完成 plan -> run -> report -> gate，JSON 只输出最终 manifest
atk smoke --base main --head HEAD --env staging --title "优惠券下单" --format json \
  > /tmp/atk-smoke.json

# 只有发现覆盖不足或要起草场景时，再读取确定性上下文
atk context --base main --head HEAD --format json > /tmp/atk-context.json

smoke 会写入 .atk/last-run.json。AI 应读取它的 failed_scenarios、intents_pending 和 next，而不是从终端输出手工搬运 run_id。atk plan 仍可单独建运行记录，但不是功能验证的默认入口。

AI 必须读取：

  • 变更文件和 patch。
  • 受影响模块。
  • 现有场景，避免重复。
  • 相关 controller/router/service/component/schema。
  • 需求说明或提交说明中的业务约束。

5.2 生成 API 场景

API 场景必须来自代码事实，按证据优先级生成：

证据AI 要提取什么
路由/controllermethod、path、query/path/body 参数。
DTO/schema/OpenAPI字段名、类型、必填、枚举、响应结构。
service/handler业务分支、状态机、权限、幂等、错误码。
现有场景登录方式、token、fixture、capture 风格。

API 场景要求：

  • 每个场景一个业务意图。
  • expect 必须包含 status 和关键业务字段。
  • 不得只断 status: 200。
  • 不得编造不存在的接口、字段或错误码。
  • 草稿必须带 ai-generated tag。
断言能力（别再只断 status）：除相等外，expect 还支持比较、包含、正则、长度、类型、枚举。 字面量以反斜杠开头可转义。 
expect:
  status: 200
  data.orderNo: not_null
  data.payAmount: "< 90"          # 比较：< <= > >= == !=
  data.msg: "contains: 成功"        # 包含 / not_contains
  data.mobile: "regex: ^1[3-9]\\d{9}$"
  data.items: "len: 3"             # 或 "len: 1..5"
  data.id: "type: str"
  data.state: "in: [pending, paid]"
  data.err: is_null
复杂值可用列表式：expect: [{ path: data.payAmount, op: lte, value: 90 }]。 
scenario: 优惠券下单后金额扣减
module: order
priority: P0
tags: [ai-generated, smoke, api]
env: staging
steps:
  - api:
      call: "POST /api/login"
      body: { username: "${username}", password: "${password}" }
      expect: { status: 200, data.token: not_null }
      capture: { token: "data.token" }
  - api:
      call: "POST /api/orders"
      headers: { Authorization: "Bearer ${token}" }
      body: { skuId: "${test_sku}", qty: 1, coupon: "WELCOME10" }
      expect: { status: 200, data.discount: 10 }
      capture: { order_no: "data.orderNo" }

5.3 生成 E2E/UI 场景

E2E 场景也必须来自代码或页面证据。AI 应优先寻找：

  • 前端路由和页面入口。
  • 表单字段、按钮、菜单、文案。
  • data-testid、aria label、稳定文本。
  • 页面调用的 API 和响应字段。

UI 步骤写业务语义和稳定定位线索，不写坐标，不写“页面正常”。当前 atk run 不执行 UI，所以 UI/E2E 的确定性结果来自 AI 浏览器实测后的 record。

scenario: 页面下单后列表显示待支付
module: order
priority: P0
tags: [ai-generated, smoke, e2e]
env: staging
steps:
  - ui:
      action: 打开订单创建页面，填写商品、数量和优惠券并提交订单
      expect: 提交成功后跳转到订单列表或详情页
  - ui:
      action: 在订单列表搜索刚创建的订单
      expect: 列表出现该订单，状态为待支付，金额已扣减优惠券

5.4 校验草稿

# 草稿先做语法与 DSL 校验
atk validate

# 人确认 expect 后才转正；reject 必须补 --note
atk review-draft scenarios/order/gen-abc123-1.yaml --by dev --verdict approve

# 转正后重新建单并执行，--last 自动指向这次最新记录
atk smoke --base main --head HEAD --env staging --title "优惠券下单" --format json

如果失败，AI 先判断失败类型：

失败类型处理
配置错误修正 env、fixture、变量、请求格式。
环境错误记录 blocked 或提示检查环境。
断言失败不要擅自改成 pass；整理证据给人判断。
UI 待实测（ui_pending）用项目配置的浏览器工具实测，并通过 record --last 回填；未回填时 gate 拦截。

6. AI 浏览器实测与回填

AI 使用项目配置的浏览器工具（atk init 默认写入 ego-browser）完成 UI/E2E intent 后，必须把结论写回 atk 运行记录。

{
  "title": "页面下单后列表显示待支付",
  "status": "pass",
  "note": "创建订单后在列表查到该订单，状态待支付，金额已扣减优惠券",
  "evidence": ["/tmp/atk-order-list.png"]
}
atk record --last --from-json /tmp/atk-ui-result.json
status何时使用要求
pass断言明确成立最好带截图证据。
fail问题可复现必须带 note，写复现步骤和证据。
suspectAI 不确定，疑似问题必须带 note，等待人定性，gate 拦截。
blocked登录、权限、环境、服务不可用说明阻塞原因，不得标 pass。

pending 由含 ui: 步骤的运行自动登记，不能作为 atk record --status 的值；对同名 title 回填会原地更新该 pending 意图。

7. 完整命令流程

AI 主导，本地/TUI 中执行

# 1. 建测试单并跑已有确定性场景（--format json 只输出 manifest，含 next 建议）
atk smoke --base main --head HEAD --env staging --title "优惠券下单" --format json

# 2. 如发现缺场景，AI 按 docs/AI_AUTHORING_PROTOCOL.md 起草 YAML
atk context --base main --head HEAD --format json > /tmp/atk-context.json

# 3. 校验草稿；人审 expect 后转正或驳回
atk validate
atk review-draft scenarios/order/gen-abc123-1.yaml --by dev --verdict approve

# 4. 转正后重新 smoke，得到覆盖草稿的新运行记录
atk smoke --base main --head HEAD --env staging --title "优惠券下单" --format json

# 5. AI 浏览器实测 UI/E2E 后回填（--last 免拼 run_id）
atk record --last --from-json /tmp/atk-ui-result.json

# 6. 人做整单确认
atk review --last --by dev --verdict approve

# 7. 输出门禁结论
atk gate --last --format json
atk report --last
run_id 不必手工搬运：plan / smoke / run --record-new 会把 run_id 写入 .atk/last-run.json，后续 record / report / review / gate 一律用 --last；atk last 可查看当前操作对象。
UI 步骤不再"必然受阻"：atk run 遇到 ui: 步骤会标记为 待实测（既不计失败也不计受阻，不返回 exit 2），并自动登记为 pending 意图。 AI 实测后 atk record --last 回填；未回填前 atk gate 拦截。 门从 run 阶段移到 gate 阶段，既消除误报噪音，也保证"没测过不会说通过"。 如确需忽略 UI，用 atk run --skip-ui。

CI 中执行

# 推荐：CI 以 smoke 为单一入口；输出为机器可读 manifest
atk smoke --base origin/main --head HEAD --env staging --title "$PR_TITLE" \
  --junit reports/junit.xml --format json > reports/atk-smoke.json

# UI 待实测、草稿未转正、断言失败或漂移都会让 gate 返回非 0。
# 无需引用未定义的 $RUN_ID；需要检查当前记录时用：
atk last --format json

8. 防漂移规则

  • AI 不得编造接口、字段、状态码、页面入口、业务文案。
  • AI 不得把环境/账号问题写成业务失败。
  • AI 不得把 blocked 改成 pass。
  • AI 不得修改既有场景；草稿只增不改。
  • AI 不得跳过 atk validate 和草稿实测。
  • 人只审业务断言，不承担命令编排和日志归纳。
  • CI 只信 atk 运行记录和 gate，不信聊天记录中的口头结论。
