atk AI Test 框架优化路线图

目标不是再造一个传统测试平台，而是让研发在 product dev loop 中把“整次需求/整次提交”的测试责任交给 AI 主导、框架留痕、CI 守门、人做业务判断。

关于 AI 场景生成的结论： 当前仓库没有内置生成命令，只有 atk-authoring skill 和 atk.generator.context 上下文包模块。不要新增“atk 命令内部直接调用 LLM 生成用例”的方向。你的实际使用方式是在 TUI/CLI Agent 中结合终端命令推进，LLM 调用应该留在 Agent 编排层；atk 只提供确定性上下文、校验、运行、记录、报告、门禁和机器可读协议。

1. 当前项目定位

能力当前状态评价
YAML 场景库已实现，文件是事实源方向正确，适合 AI 读写、git review 和 CI 回放。
API 执行已实现支持 env、fixture、变量 capture、断言和报告，当前最扎实。
变更上下文atk context 已实现能提供 diff、提交、模块和现有场景，但影响面分析仍偏浅。
一键冒烟atk smoke 已实现能串起 plan/run/report/gate，但 UI 和 AI 生成仍在外部 Agent 流程。
UI 测试YAML 可写 ui:，执行器未真正支持目前是“记录外部实测结果”，不是框架内 E2E 执行。
Web 控制台场景浏览、编辑、运行、历史更像 YAML 编辑器，还不是 AI test 工作台。
CI 门禁有样例，有 gate适合 API/YAML 回归；对整次需求级 AI test 还缺覆盖缺口和 intent 强约束。

2. 推荐总架构

需求讨论 -> SPEC / design -> AI coding -> AI review -> 人工 review（可选） -> AI test（atk 负责确定性骨架，Agent 负责智能编排） -> CI gate -> QA 体系测试 -> 验收 反馈回路： test/report/gate 中的问题 -> 优化 design / 修实现 / 补场景资产

核心分层应改成下面这样：

层负责什么不负责什么
atk core上下文包、计划、运行、记录、报告、门禁、格式协议不直接自由发挥业务判断，不强绑某个 LLM。
TUI/CLI Agent读上下文、生成草稿、调用浏览器、解释失败、组织人工确认不绕过 atk 记录，不口头宣称通过。
CI确定性执行 gate、归档报告、阻断合并不做开放式 LLM 推理作为放行依据。
Dev/QA审 expect、定性 suspect/fail、确认整单不再手工重复点冒烟主路径。

3. 为什么不要内置 LLM 生成命令

不建议的形态

# 不建议新增这种命令形态：
# atk 内部拼 prompt、调 LLM、写 YAML

问题：模型、密钥、上下文裁剪、工具调用、人工暂停点都会和 Agent/TUI 重复。框架会很快变成半个 Agent 平台，维护成本高，灵活性低。

建议的形态

atk context --format json --base main
atk plan --format json --base main
# Agent 在 TUI/CLI 中读 JSON，自己生成草稿
atk validate
atk run --tags ai-generated
atk review-draft ...
atk gate ...

atk 输出确定性事实，Agent 负责智能编排。这样更符合你“结合终端 command 使用”的目标。

保留的不是新的生成命令，而是“生成协议”。也就是：上下文 JSON schema、草稿文件命名规则、expect 审查清单、失败回填 JSON schema、gate policy。这些才是框架该沉淀的能力。

4. 阶段路线

阶段目标应交付验收标准
P0校准现状 先让框架诚实、可安装、可诊断。 修正文档中“UI 执行器已完成”的表述；修复 console 静态资源打包；新增 atk doctor；清理发布包无关文件。 新项目安装后 atk init && atk doctor && atk console 能明确告诉用户哪些配置缺失。
P1机器可读协议 让 TUI/CLI Agent 不再解析自然语言输出。 为 plan/gate 增加 --format json；提供 record --from-json；后续再评估 smoke/report 的 JSON 输出。 Agent 可以用稳定 JSON 驱动流程，CI 可以稳定提取 run_id、失败清单、待办清单。
P1测试单工作流 把“整次需求/整次提交”变成一等对象。 扩展 RunRecord：required_intents、coverage、drafts、triage、review SLA；新增 atk task 或增强 atk plan。 一次变更能看到复用场景、未覆盖意图、AI 草稿、人工确认、gate 结论。
P1覆盖缺口 让 AI test 知道“还没测什么”。 模块映射升级：路径规则 + 路由/API 元数据 + OpenAPI/页面清单；输出 required_intents。 改一个接口或页面时，plan 能指出已有场景覆盖了哪些，缺哪些 intent。
P2Agent 生成适配 不做内置 LLM，但给 Agent 最短路径。 提供 atk-authoring 协议；增强 atk context --format json 字段；后续提供 expect 摘要命令、review-draft 批量模式。 Agent 在 TUI/CLI 里能稳定生成 1-5 个草稿，并让人只审 expect。
P2UI 实测协议 先把外部浏览器实测标准化。 新增 atk ui-plan 输出 UI intent；Agent 用 ego-browser/Playwright 操作；record --from-json 回填步骤、截图、DOM 摘要。 UI 实测不再靠口头和自由文本，报告能复现每个关键证据。
P3确定性 E2E 把高价值 UI intent 固化为可回归资产。 从自然语言 UI step 生成 Playwright 脚本或结构化动作；失败时区分选择器失效和业务断言失败。 夜间回归能自动跑核心 UI 流程，不依赖每次 Agent 重新看页面。
P3工作台 控制台从 YAML 编辑器升级为 AI test 工作台。 测试单列表、覆盖缺口、草稿 expect 审查、intent 回填、失败定性、gate policy 配置。 开发不用记命令串，在控制台/TUI 里能看到整次需求测试状态。

5. 建议命令边界

命令建议保留/增强说明
atk context增强成为 Agent 的事实输入。重点是 JSON schema 稳定、上下文足够完整。
atk plan增强输出复用场景 + required_intents + coverage，不只是 affected_modules。
atk smoke保留作为一键确定性入口，但要明确“不执行开放式 UI Agent”。
atk run保留负责 API/YAML 确定性回放；后续可接确定性 Playwright。
atk record增强支持 --from-json，强制 fail/suspect 带 note，按 policy 要求 evidence。
atk review-draft增强支持 expect 摘要、批量评审、评审人和时间记录。
atk gate增强读取 gate_policy.yaml，按团队强度决定 blocked/review/evidence 是否拦截。
atk-authoring skill保留但重新定位它是 Agent/TUI workflow 的说明和协议，不是 atk CLI command；不要让 atk 内部调用 LLM。

6. 推荐 TUI/CLI Agent 工作流

# 1. Agent 获取确定性事实
atk context --base main --head HEAD --format json > /tmp/atk-context.json
atk plan --base main --head HEAD --format json > /tmp/atk-plan.json

# 2. Agent 判断是否需要补草稿
# 生成 scenarios/<module>/gen-<sha>-N.yaml，不通过 atk 内置 LLM
atk validate
atk run --env staging --tags ai-generated

# 3. 人审 expect，Agent 只负责整理清单和执行命令
atk review-draft scenarios/order/gen-abc123-1.yaml --by dev --verdict approve

# 4. 确定性回归
atk smoke --base main --head HEAD --env staging

# 5. UI intent 外部实测后结构化回填
atk record "$RUN_ID" --from-json /tmp/atk-ui-result.json

# 6. 整单确认与门禁
atk review "$RUN_ID" --by dev --verdict approve
atk gate "$RUN_ID" --format json

7. RunRecord 应扩展的核心字段

schema_version: 2
run_id: smoke-20260909-153000
title: 下单链路
base_ref: main
head_ref: HEAD
affected_files: []
affected_modules: []
coverage:
  reused_scenarios: []
  missing_intents: []
required_intents:
  - id: order-create-coupon
    source: diff
    module: order
    title: 优惠券下单校验
    status: pending
drafts:
  - file: scenarios/order/gen-abc123-1.yaml
    status: pending_review
triage:
  fail: []
  suspect: []
reviews: []
gate:
  policy: strict
  verdict: blocked

8. Gate Policy 建议

# config/gate_policy.yaml
require_review: true
require_evidence_for_ui: true
fail_on_blocked: false
fail_on_unmapped_files: true
run_ttl_minutes: 120
require_all_required_intents_done: true
allow_environment_blocked_in_mr: true
allow_environment_blocked_in_release: false

这样可以区分个人试用、MR 门禁、发布门禁三种强度。当前代码里 review reject 只告警、blocked 不拦截，对原型友好，但对团队发布偏宽。

9. 控制台/TUI 应该长什么样

页面/视图核心信息用户动作
测试单列表需求标题、分支、run_id、gate 状态、待办数进入详情、重跑、归档
测试单详情diff 摘要、影响模块、复用场景、缺口 intent触发 Agent 补草稿、触发 smoke
草稿评审草稿路径、请求、expect 摘要、实测结果approve/reject expect
UI 实测intent、步骤、截图、DOM 摘要、状态标记 pass/fail/suspect/blocked
失败定性失败场景、断言 diff、截图证据、根因猜测确认 bug/误报/环境问题
Gatepolicy、阻断项、告警项、CI 链接重新 plan、重新 run、生成报告

10. 最短落地顺序

  1. 修正文档与打包，保证别人装完能用。
  2. 给 plan/smoke/gate 加 JSON 输出，先服务 TUI/CLI Agent。
  3. 扩展 RunRecord，加入 required_intents 和 coverage。
  4. 强化 record，支持 JSON 回填和 policy 校验。
  5. 做控制台“测试单详情页”，先不做复杂 AI 功能。
  6. 把 UI 实测作为外部 Agent 协议标准化。
  7. 最后再考虑 Playwright 固化和自修复。

判断标准：一个开发者完成一整个需求后，只需要告诉 TUI/CLI Agent“验证这次改动”。Agent 能通过 atk 的确定性命令完成建单、补草稿、跑回归、实测 UI、收证据、请人审 expect、输出 gate 结论。所有关键结果都落在 run record 和报告里，而不是散落在聊天记录中。
